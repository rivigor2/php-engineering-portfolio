# CRM ↔ электронный документооборот

В коммерческой интеграции я дорабатывал получение пакетов, подпись актов, автозаполнение полей и работу с полномочиями подписанта. Здесь заново реализован обезличенный срез: **пакет → акт → полномочия → запись CRM → поля и статус → результат доставки**. Исходники компании и реальные документы не публикуются.

## Открыть код

- [ApplyIncomingPackage](src/Application/ApplyIncomingPackage.php) — сквозная операция: полный хеш пакета, проверка повтора, загрузка связи с CRM, запись изменений и receipt в одной локальной транзакции.
- [CLI-сценарий](bin/document-package.php) — три синтетических пакета; каждый обрабатывается дважды, выводится сохранённая CRM-проекция.
- [MapActToCrmFields](src/Application/MapActToCrmFields.php) — номер, календарная дата и денежная сумма без float.
- [PdoDocumentFlowStore](src/Infrastructure/SQLite/PdoDocumentFlowStore.php) — привязка по организации и ID документа, версия записи, журнал доставок.
- [ProcessIncomingPackage](src/Application/ProcessIncomingPackage.php) и [PlanIncomingPackage](src/Application/PlanIncomingPackage.php) — квитанция отдельно от акта, связь с CRM и ручной разбор.
- [Authority](src/Domain/Authority.php) / [VerifiedAuthorityProvider](src/Application/VerifiedAuthorityProvider.php) — подтверждения для конкретного документа.
- [ReconcileDocumentFlow](src/Application/ReconcileDocumentFlow.php) — допустимые переходы, повторы, разрывы и регрессии.

## Сценарии

[Разрешённый акт](examples/incoming-package.json): служебная квитанция исключается, акт связывается с существующей записью. При received → ready_to_sign заполняются номер, дата и сумма; готовится запрос человеческого подтверждения. Сумма 12500.50 хранится как 1250050 минимальных денежных единиц; дата документа не переводится между часовыми поясами.

[Истёкшая доверенность](examples/authority-refused.json): остальные признаки сохранены; ручной разбор без изменения CRM-проекции.
[Пропуск статуса](examples/status-gap.json): received → completed не подтверждается; локальное состояние сохраняется.

Повтор доставки не записывает документ и не запрашивает подтверждение заново. Сохраняется ранее полученный результат, включая manual_review. Тот же ID доставки с другим телом отклоняется. Исправление уже заполненных полей акта требует отдельного разбора, а не молчаливой перезаписи. После ручного разбора повторная оценка полномочий должна быть отдельным управляемым действием; обычный retry её не выполняет.

Из корня репозитория:

    php current-experience/b2b-document-flow/bin/document-package.php

CLI использует реальную SQLite в памяти и синтетические серверные связи с CRM. Внешняя CRM и оператор ЭДО не вызываются. Контракт примера ограничен актами в RUB: суммы передаются десятичной строкой, в хранилище — целым числом копеек.

## Границы

Authority получает проверенные данные для конкретного документа из доверенного серверного адаптера; пользовательские флаги не доказывают полномочие. CLI использует только явно синтетические признаки. Криптография, отзыв сертификата, проверка МЧД у оператора и настоящая подпись здесь не реализованы. Разрешение запросить подпись не означает наличие подписи.

SQLite-схема, нормализованные поля и receipt — решения самостоятельной публичной реализации, не описание внутренней БД или полного коннектора компании. Атомарность действует только для локальной CRM-проекции и журнала доставки; внешняя CRM-запись и доставка запроса подписи не реализованы. Частичный пакет может содержать применённые документы и отдельный ручной разбор. Мой вклад в коммерческой системе — доработки актов, пакетов и полей, без приписывания всей платформы.
