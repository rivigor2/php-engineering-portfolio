# CRM: задачи и персональные стадии Scrum

В корпоративном портале я дорабатывал отображение и управление стадиями Scrum из карточки задачи. Предметное правило: **показывать стадии текущих исполнителей, сохранять историю бывших, менять стадию только по актуальным правам и состоянию задачи**.

Здесь правило и серверный контур заново реализованы на синтетических данных. Это не исходники портала и не его схема хранения.

## Начать с кода

1. [ChangeTaskParticipantStage](src/Application/ChangeTaskParticipantStage.php) — серверная операция: загрузить контекст, проверить версию и допустимость изменения, передать сохранение адаптеру.
2. [TaskParticipantStages](src/Application/TaskParticipantStages.php) — видимая проекция и изменение одной стадии с сохранением бывших участников.
3. [PdoTaskStageGateway](src/Infrastructure/SQLite/PdoTaskStageGateway.php) — SQLite-хранилище, повторная загрузка прав/доски/участников под блокировкой, сохранение и увеличение версии.
4. [HTTP-обработчик](src/Infrastructure/Http/TaskStageController.php) — серверная личность, CSRF, входные поля и конфликт версии 409.
5. [TaskStageGateway](src/Application/TaskStageGateway.php) — контракт для серверного адаптера.
6. [Исполняемый сценарий](bin/task-stages.php) и [входные данные](examples/task-participant-stages.json) — одно изменение и три отказа.

## Один сценарий

В задаче два текущих исполнителя. В хранилище осталась стадия бывшего исполнителя. Карточка показывает только текущих; новый участник получает not_assigned, а не чужую стадию.

Уполномоченный пользователь меняет стадию нового участника. Сервер получает участников, разрешённые стадии выбранной доски и права **из хранилища**. Перед записью адаптер повторно читает контекст под блокировкой: отзыв доступа, смена состава, доски или версии не позволяют сохранить устаревшее изменение.

Операция сохраняет прежние записи и увеличивает версию. В примере далее отказываются изменение бывшего участника, запрос без права редактирования и запрос со старой версией. Сохранение того же значения не повышает версию.

Из корня репозитория:

    php current-experience/crm-workflow-backend/bin/task-stages.php

CLI создаёт изолированную SQLite-базу в памяти, загружает синтетический серверный контекст и печатает проекцию и сохранённую историю. Это исполняемый пример без доступа к Bitrix.

## Границы

В HTTP-адаптере личность актёра берётся из авторизованной серверной сессии. Клиент передаёт выбранного участника, стадию и ожидаемую версию, но не может объявить себе права или заменить состав задачи. Значения session_actor_id в CLI обозначают только синтетические сессии.

Контракт версии охватывает изменения задачи, состава, доски и правил редактирования. SQLite-адаптер дополнительно сравнивает прочитанный контекст и повторяет предметную проверку под блокировкой. При конфликте требуется обновить карточку; автоматического повторения устаревшего действия нет.

SQLite — выбор публичной реализации. D7/ORM, REST-авторизация и интерфейс настоящего портала здесь не воспроизводятся. Безопасный повтор внешнего REST-действия и подтверждённая установка в Bitrix не заявляются.

## HTTP-граница

[TaskStageController](src/Infrastructure/Http/TaskStageController.php) показывает получение карточки и запрос изменения. Приложение передаёт проверенную личность сессии и результат проверки CSRF; JSON не задаёт права, актёра, участников или доску. Конфликт версии возвращается как HTTP 409, ошибки доступа — 401/403. Контроллер возвращает структуру ответа для интеграции с framework; готовый HTTP-сервер и авторизация портала здесь не реализованы.
