# i-CDM — PHP/Node.js и изолированные исполнители

Личный проект автоматизации: создать задание в PHP-панели, перевести его в обработку, выполнить команды через отдельного исполнителя и получить результат. Исполнители использовали Telegram API; их контейнерами управлял собственный Node.js-модуль.

**Версия фрагментов:** 2023. Источник — мой репозиторий i-cdm.

## Начать с двух мест

1. [services.php: очередь авторизации исполнителей](code/services.php#L166) — получение записей, состояние обработки, выполнение команды и разбор результата.
2. [swarm.js: создание контейнера](code/swarm.js#L268) и [запуск](code/swarm.js#L47) — жизненный цикл изолированного исполнителя.

Swarm — название класса этого приложения. Показанный код использует Docker API для контейнеров; он не подтверждает опыт эксплуатации кластера Docker Swarm.

## Моя работа

Я разрабатывал связку PHP-задач, сервиса обработки, управления контейнерами и API-исполнителя. В выбранном срезе видно разделение состояния задания, управляющего процесса и среды выполнения. Интерфейс панели и полная схема БД не включены.

## Три части реализации

    Управление заданием:   PHP-панель → запись задания → Q_START / Q_END
    Сопровождение:        очередь авторизации → PHP-сервис → результат / статус
    Среда исполнителя:    Node.js HTTP API → Docker → PHP-runner → Telegram API

Это карта подсистем. Связывающие модульные функции и диспетчер рабочих заданий не входят в выборку: очередь авторизации ниже нельзя считать обработчиком всех пользовательских задач.

- [jobs/create.php](code/jobs/create.php) создаёт запись задания или возвращает найденную при повторе идентификатора. Начальные значения в этом фрагменте — шаблон для формы, не заполненное пользовательское задание.
- [jobs/start.php](code/jobs/start.php) проверяет существующую запись и переводит модуль и связанные очереди в Q_START.
- [jobs/stop.php](code/jobs/stop.php) задаёт Q_END для модуля и связанных очередей.
- [_job_queues_auth](code/services.php#L166) получает записи авторизации со статусами N/S, помечает обработку и различает запрос кода подтверждения, ошибку API и сбой исполнителя по выводу команды.
- [_sync_droids](code/services.php#L113) переносит код в контейнеры и собирает их журналы.
- [Swarm](code/swarm.js#L86) предоставляет управляющие HTTP-маршруты и операции контейнеров.
- [telegram-runner.php](code/telegram-runner.php#L81) проверяет состояние API-сессии; [обработчик команды](code/telegram-runner.php#L158) показывает вызов API, разбор RPC-ошибки и возврат результата.

## Как читать границы

Q_START/Q_END относятся к состоянию модуля и очередей. N/S в сервисе — другая шкала состояния обработки. Назначение остановки задания в БД не является доказательством немедленной отмены уже выполняющегося внешнего действия.

__DB, get_queue, set_status_queue и модульные функции — зависимости исходной PHP-платформы. Файловые сигналы и каталоги соединяли сервисы; Docker и Telegram-библиотеки не включены. Конфигурации, сессии и настоящие ключи удалены из публичной выборки; пути заменены.

## Почему это часть портфолио

Код показывает PHP/Node.js-интеграцию, очередь, управление ресурсами исполнителя и сопровождение его состояния. [Разбор сегодня](CURRENT_REVIEW.md) объясняет, какие гарантии здесь ещё нельзя считать обеспеченными и что я менял бы первым.

Это историческая подборка для чтения. Она не является готовым сервисом или комплектом для запуска против Telegram.
